# Implementation Plan: SEO y descubribilidad — Nivel 1

**Branch**: `002-seo-y-descubrimiento` | **Date**: 2026-05-29 | **Spec**: [./spec.md](./spec.md)

**Input**: Feature specification from `./spec.md`

## Summary

Implementar los quick wins técnicos de SEO sobre la landing pública usando exclusivamente primitivas de Next.js 16 (`generateMetadata`, `MetadataRoute.Sitemap/Robots/Manifest`, `ImageResponse` para OG image). El alcance es mecánico — sin decisiones de RLS, sin migraciones, sin nuevas dependencias.

Estructura:

- **Metadata** en `src/app/page.tsx` (landing) extendida con OG/Twitter/canonical/JSON-LD.
- **Endpoints nuevos**:
  - `src/app/sitemap.ts` → `/sitemap.xml`
  - `src/app/robots.ts` → `/robots.txt`
  - `src/app/manifest.ts` → `/manifest.webmanifest`
  - `src/app/opengraph-image.tsx` → `/opengraph-image` (PNG 1200×630)
  - `src/app/apple-icon.tsx` (o asset estático) → `/apple-icon`
- **Variable de entorno nueva** `NEXT_PUBLIC_SITE_URL` documentada en `docs/development.md` (legacy doc — pero sigue siendo el lugar canónico para variables de entorno) y referenciada desde un helper compartido `src/lib/seo/site-url.ts`.
- **`noindex`** explícito en las rutas transaccionales (`/auth/callback`, `/auth/confirm`, `/auth/signout`, `/q/[code]`).

Validación con Lighthouse local + smoke manual de previews en WhatsApp/X después del deploy. Submit manual a Google Search Console (fuera del scope automatizable).

## Technical Context

**Language/Version**: TypeScript ^6, React 19.2.6, Next.js 16.2.6.

**Primary Dependencies**: Solo primitivas nativas de Next 16:

- `next/metadata` — `Metadata`, `MetadataRoute`
- `next/og` — `ImageResponse` para generar la OG image como PNG
- Tipos generados de Supabase si la sitemap necesita listar matches en algún futuro (no en este nivel)

**Sin nuevas dependencias** externas (constitución y FR-015).

**Storage**: N/A. Los endpoints son puramente computacionales — no leen DB.

**Testing**:

- **Unit tests** sobre `src/lib/seo/site-url.ts` (resolución del URL absoluto a partir de env var con fallback).
- **No tests de Next pages** — la primitiva `generateMetadata` es de Next, no de la app. Se valida con Lighthouse y validadores externos (manual).

**Target Platform**: Web. Sin requisitos especiales.

**Project Type**: Web application (Next.js App Router, brownfield).

**Performance Goals**:

- `/` se sirve igual de rápido que hoy: las metadata son estáticas; la OG image se cachea por Next.
- Bundle size no crece >20 KB netos (SC-006).

**Constraints**:

- Respeta RLS (no aplica — los endpoints no leen DB).
- Sin nuevas dependencias.
- Sin migraciones.
- Server Components / Server primitives only.

**Scale/Scope**: Trivial. Cambios mecánicos sobre ~6 archivos nuevos + 1-2 modificados.

**Structure Decision**: Sigue el patrón Next 16 — los endpoints especiales (`sitemap.ts`, `robots.ts`, `manifest.ts`, `opengraph-image.tsx`, `apple-icon.tsx`) viven directamente bajo `src/app/` por convención del framework. El helper compartido vive en `src/lib/seo/` agrupando lo SEO-específico.

Para las rutas `route.ts` (auth callbacks, q-code): no renderean HTML, son handlers de redirect. NO necesitan `metadata` — `robots.txt` Disallow ya las cubre. Si en algún momento estos handlers comienzan a renderear HTML transitorio, agregar `noindex` ahí.

## Complexity Tracking

| Decisión no obvia | Por qué | Alternativa más simple rechazada porque |
|---|---|---|
| Variable de entorno nueva `NEXT_PUBLIC_SITE_URL` en vez de hardcodear el dominio | El dominio puede cambiar (Vercel preview, custom domain, staging). Hardcodearlo crea un punto de fricción en cada cambio. | Hardcode haría más simple este PR pero crearía deuda. La constitución dice "no introducir deps nuevas" — env vars no son deps. |
| OG image generada con `ImageResponse` server-side en vez de un PNG estático | Cero mantenimiento manual de la imagen, escala a múltiples idiomas/temas si en el futuro hace falta, no agrega un binary al repo. | Un PNG estático sería más simple pero requeriría regenerar manualmente si cambia el branding. Más fricción a largo plazo. |
| Helper `site-url.ts` en `src/lib/seo/` en vez de inline | Múltiples consumidores (sitemap, robots, OG, canonical, JSON-LD) necesitan la misma resolución. DRY. | Inline en cada archivo introduciría 5+ copias del fallback lógico. |
| Apple touch icon como `apple-icon.tsx` en vez de PNG estático | Consistencia con OG image (ambos generados por Next). Si en el futuro el branding cambia, un solo archivo a tocar. | Un asset estático es trivial pero crea inconsistencia con OG image. Mejor un solo patrón. |
